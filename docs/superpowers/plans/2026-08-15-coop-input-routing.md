# Plan — couch co-op input routing: a second input, the `coop` devflag, and replay's `EncodedTick`

Status: adopted 2026-08-15, implemented on branch `coop-input`.

Provenance: adjudicated as the direct follow-on to
`docs/superpowers/plans/2026-08-15-coop-foundation.md` (`Tank.controlledBy`, per-slot
spawn via append-at-end in `loadArena`, `playerCount` threaded through
`createWorldFor`/`LevelSystem.world`, per-slot render style). That plan intentionally
stopped short of a second input, a devflag, and `ReplayMeta`/`EncodedInput` multi-input
support, naming all three as this plan's job. Every decision below was made before
implementation started; the ordered steps in §7 were followed as written, red-first,
gate-green at each step. Reproduced below as adopted, already in the project's

---

Builds on `docs/superpowers/plans/2026-08-15-coop-foundation.md` (`Tank.controlledBy`, per-slot spawn via append-at-end in `loadArena`, `playerCount` threaded through `createWorldFor`/`LevelSystem.world`, per-slot render style). That PR intentionally stopped short of a second input, a devflag, and `ReplayMeta`/`EncodedInput` multi-input support, naming all three as this PR's job. Scope here is exactly those three plus the input-construction wiring in `src/game/loop.ts`.

### 1. Input assignment and the seam for N

Today `src/input/input.ts`'s `createInputController` produces **one** merged `InputController` for keyboard+mouse+touch, optionally OR-ing `gamepad[0]` into the same stream (`?dev=1&gamepad=1`, single-player accessibility). Co-op needs P2 to have its **own** input identity, not merged into P1's — merging and co-op are different features that happen to both want `gamepad[0]`.

Decision: **repurpose the gamepad reader as a standalone per-slot source, don't extend the merge.** Add a new stateful wrapper in `src/input/gamepad.ts` (consistent with that file's existing pure-core/stateful-edge split: `deadzoneVector` pure, `createGamepadReader` stateful, this is a third layer on top of `createGamepadReader`) — `createGamepadInputSource(getGamepads): PlayerInputSource` where `PlayerInputSource = { sample(): InputState; setPlayerPosition(pos): void; gamepadConnected(): boolean; dispose(): void }`. Internally: hold its own `aim: Vec2 = {0,0}` (default, self-corrects on first stick deflection) updated only when `poll().aim !== null` — `GamepadReader.poll()` returns `aim: null` inside the dead zone, and the merged controller survives that because mouse/touch keep `aim` alive; slot 1 has no such fallback and needs its own persisted value. Quantize through the same boundary everything else converges on: `quantizeAim` currently lives un-exported in `input.ts`; relocate it to `src/input/touch.ts` (already imported by both `input.ts` and `gamepad.ts`, so this avoids introducing an `input.ts`↔`gamepad.ts` import cycle) so slot 1 reuses the identical quantization rather than a second copy.

Coexistence with `?dev=1&gamepad=1`: **mutually exclusive by construction, not by convention.** When `coop` is on, slot 0 is always built with `{ gamepad: false }` regardless of `devFlags.gamepad`'s value — the merge reader is never constructed, mirroring the codebase's own idiom ("off means the reader is never even constructed, not merely that its output is discarded"). Slot 1 owns `gamepad[0]` exclusively. No conflict is possible by inspection, not just by test.

The seam for N later: `loop.ts` holds an array `slots: PlayerInputSource[]`, index = `controlledBy` slot, `slots[0]` always the multi-device controller, `slots[1]` (when `coop`) the gamepad-alone source. Adding gamepad[1] or a keyboard split later is populating `slots[1]`/`slots[2]` differently — no change to the driver, recorder, or replay layers, all of which only ever see "the list."

### 2. The flag

`coop: boolean` in `src/game/devflags.ts`'s `DevFlags`/`DEV_FLAGS_OFF`, parsed with the existing `isOn(params, 'coop')` idiom — same shape as `invincible`/`autoplay`, not valued like `quality`. Boolean is the honest shape: this PR wires exactly one additional input source (gamepad[0] → slot 1), so `?dev=1&coop=1` means playerCount 2, full stop. A valued `coop=N` would advertise a capability (N>2 assignment) that doesn't exist yet — the same "don't architect for an absent consumer" reasoning the foundation plan already used to defer `ReplayMeta.playerCount`. Upgrade to valued when a third real source (gamepad[1], keyboard-split) exists, not before.

**Not in the `playtest` bundle** — that bundle is single-player numeric playtesting (`invincible`/`shellCount`/`mineReach`/`mineTimer`); co-op is an orthogonal, riskier experimental mode a shared `?playtest=1` link must not silently enable.

**Sandbox: excluded.** `createLevelSystem`'s sandbox branch (`src/game/levels.ts:88-101`) calls `createSandboxWorld` directly, which takes no `playerCount` — no `loadArena` call to inherit the spawn-offset rule from, and no ring-search/fallback mechanism exists for a hand-built single-`'P'` grid. Rather than building sandbox-specific P2 placement (real work, out of scope), `coop` is read but never wired when the active `LevelSystem` is the sandbox one: no slot-1 source is constructed, `playerCount` passed to `world()` stays 1. This is the concrete "prevents nonsense" guard — without it, `?dev=1&coop=1&level=sandbox` would either need to silently no-op (confusing) or spawn a P2 with no valid spawn cell to receive it.

### 3. Driver/step boundary

`src/sim/world.ts`'s `step(world, input)` stays exactly the one-line adapter it is (`stepInputs(world, [input])`) — nothing here touches it, and `tools/baseline/trace.ts`/`src/game/replay.ts`'s existing single-input callers keep using it unmodified.

Decision: `src/game/driver.ts`'s `DriverDeps.input` changes from `{ sample(): InputState }` to `{ sample(): InputState[] }`, and the frame loop's `step(curr, deps.input.sample())` (driver.ts:120) becomes `stepInputs(curr, deps.input.sample())`. **Always list-shaped, even at playerCount 1** — no `if (playerCount === 1) step() else stepInputs()` branch in the driver. This is the shape that makes N players "data, not rework" (one code path, list length varies) and it costs nothing at N=1: `src/sim/step-inputs.test.ts`'s own "step() is an adapter over stepInputs" describe block already proves `stepInputs(world, [input])` produces a world/events `toEqual` what `step(world, input)` produces, byte for byte. So a 1-length list through `stepInputs` is *proven*, not merely argued, to be value-identical to today's driver at playerCount 1.

That sim-level proof doesn't cover driver.ts's own wiring (composition blindness — the exact trap CLAUDE.md names for `step-pipeline.test.ts`). This PR needs a driver-level test making the same claim one layer up: feed the OLD driver-shape fixture as a 1-length list, assert the resulting world/events equal what a `step()`-based driver would have produced.

`frame.ts`'s `renderAlpha`/`animationDt`/`planFrame` were read and carry no coupling to "the" input at all — pure functions of `dt`/`acc`/`GameState`. No changes there.

### 4. Replay

`src/game/replay.ts`'s `EncodedInput` (5-tuple) stays as the single-player-slot encoding, reused per slot. Add `EncodedTick = EncodedInput[]` (one entry per active slot, slot order = `stepInputs` pairing order) and `encodeTick`/`decodeTick` (`map` over `encodeInput`/`decodeInput`). `ReplayTrace.ticks: EncodedTick[]`.

`ReplayMeta` does **not** grow a `playerCount` field with its own plumbing — derive it off the world at record time (`world.tanks.filter(t => t.kind === 'player').length`), matching the file's own stated convention ("read off the world rather than off the flags that produced it") and keeping `replayMetaFor(world, arenaId)` at its existing two-argument shape. This count equals the recorded array length by construction (kind is `'player'` for every human-controlled tank regardless of whether `controlledBy` is stamped).

`REPLAY_SCHEMA` bumps 1 → 2: this is exactly what `schema` exists for ("can this build parse the trace") per its own doc comment, and the codebase has no migration layer anywhere for replays — a mismatch is already treated as outright rejection (`checkTrace`), never reinterpreted. `?dev=1&replay=1` traces are a dev-console debug capture, not user save data, so rejecting old ones rather than reading them under a new shape is the low-risk, in-convention choice. Grepped: no test hardcodes the literal `1` outside importing the `REPLAY_SCHEMA` const, so bumping it doesn't silently break an unrelated pin.

`replayTrace(trace, world)` (replay.ts:302) switches its inner call from `step` to `stepInputs`, decoding via `decodeTick`. It deliberately does **not** call `checkTrace` (documented as the "deliberately-stale-replay" path) — that path's contract needs restating: it assumes the *current* schema's tick shape (an old flat schema-1 trace fed to it directly would crash `decodeTick`'s `.map` over bare numbers). Note this explicitly in its doc comment rather than adding a runtime branch — `checkTrace` is already the mechanism for a caller that wants that safety.

**Recorder's wrap point doesn't move.** `createRecordingInput` still decorates `effectiveInput` at the same position in `loop.ts`, between the raw per-slot sources and the driver — only the payload shape each `sample()` call carries changes (`InputState` → `InputState[]`). Generalize `InputSource`/`RecordingInput` in replay.ts to `sample(): InputState[]` uniformly (not a special N=1 case), since `effectiveInput` itself is now always list-producing (`slots.map((s, i) => …)`, with autoplay substituting only index 0 — autoplay predates coop and only ever demos P1; slot 1's real gamepad still samples through when both flags are set).

**Mutate-manifest collision, concrete and load-bearing:** `tools/mutate/manifest.json`'s `replay-recorder-wraps-the-raw-controller` entry mutates `createRecordingInput(effectiveInput, replayMetaFor(world, level.arenaId))` → `createRecordingInput(input, …)` on this exact line. Keeping `replayMetaFor` two-argument keeps the `find` string byte-identical, so the tool will still locate and apply it — but post-PR `effectiveInput` yields `InputState[]` while `input` (slot 0's raw controller) still yields `InputState`; `npm run mutate` doesn't run `tsc`, so this type mismatch isn't caught structurally, and at runtime the mutated recorder calls `encodeTick` on a bare `InputState`, which has no `.map` and throws. The entry's `expect: killed` may still hold but through a different mechanism (a thrown error instead of the one designed assertion), which can change `expectFailures` if the crash cascades across more `loop.test.ts` cases than the original single discriminating one. This must be re-measured, not assumed: run `npm run mutate --only replay-recorder-wraps-the-raw-controller` after the code change and update `expectFailures`/`why` to what's actually observed.

### 5. Aim for P2 / "the player" audit

`src/input/gamepad.ts`'s `poll(playerPos)` is already position-agnostic — it takes `playerPos` as a plain argument and needs no change. The only place "the player's position" is assumed is the **caller**: `loop.ts`'s `onSimulated` (loop.ts:642-649) does `w.tanks.find(t => t.kind === 'player')` once and pushes that position to the single controller. Generalize to a per-slot lookup mirroring the render seam's own adopted convention exactly (`controlledBy ?? 0`, from the foundation plan's `render/entities.ts` style map): `tankForSlot(w, slot) = w.tanks.find(t => t.kind === 'player' && (t.controlledBy ?? 0) === slot)`, then `slots.forEach((src, i) => src.setPlayerPosition(tankForSlot(w, i) ? {x, y} : null))`. At playerCount 1 this is identical to today's lookup (no `controlledBy` stamp, `?? 0` defaults to slot 0, same tank found).

Enumerated "assumes THE player" sites in `loop.ts`, and their disposition:
- `playerId` (scalar, loop.ts:510) feeding `director`/`haptics`/`stats.record`/`isPlayerDeath`/shell-count HUD/fire-signal HUD/`run.setLivesRemaining` — **all P1-only, explicitly deferred by the foundation plan's own audit** ("correct-as-P1 placeholder, semantics deferred"). Untouched here.
- `buildWorld`'s invincible stamp (loop.ts:404-407), `w.tanks.find(kind==='player')` — stays P1-only; no P2 invincible in this PR, named in deferrals.
- `input.setTouchScheme`/`setFireMode`/touch aim-stick's own internal `playerPos` — unaffected, slot 0's controller keeps getting P1's position for its own devices exactly as today.
- `gamepadConnected()`/the "Gamepad connected" toast (loop.ts:608-615, 655-657) is wired to slot 0 today; under `coop`, slot 0 has no gamepad reader (decision 1), so that toast simply won't fire for a coop pad — acceptable, named as deferred rather than silently broken, since a P2-specific connect affordance is a HUD decision out of this PR's scope.

**Load-bearing gap the advisor flagged:** the correctness of "slot i drives the tank with `controlledBy === i`" rests on the foundation's append-at-end insertion producing that exact alignment, but nothing currently pins the *agreement* between input-slot order and `stepInputs`' array-order pairing against a *real* `loadArena(arena, 2)` world — `step-inputs.test.ts` pairs by array order on a hand-built world with no `controlledBy`, and the foundation's own `loadArena(arena,2)` test checks spawn cell and `controlledBy` but not input routing. This PR must add one integration test (natural home: `loop.test.ts`, which already exists to close exactly this kind of composition-blindness gap) that builds a real `createWorldFor(arena, seed, …, playerCount=2)` world, drives it with two distinct fake sources, and asserts both that the `controlledBy===i` tank moved per slot i's input *and* that slot i's `setPlayerPosition` received that same tank's position — tying the sim's pairing contract to the input layer's slot assignment in one place.

### 6. HUD/camera

No new guard beyond the sandbox exclusion already covered in §2. The lives/win-lose P1-only behavior (`resolveStatus` watches P1 only, `world.lives` is a shared pool) is pre-existing, adjudicated debt from the foundation PR, not something this PR's mechanism newly creates — it only newly *exercises* a `controlledBy` tank that would otherwise sit inert (AI skips every `kind === 'player'` tank, so an undriven P2 tank just stands still forever). The one behavior worth stating rather than building: with `coop` on and no pad connected, `GamepadReader.poll()` already returns `NEUTRAL_POLL` when `pad == null` — P2's tank is spawned, alive, and idle until a controller is plugged in, which is a sane degrade already provided by existing code, not new nonsense.

### 7. Ordered steps, red-first, gate-green at each

1. **`src/input/gamepad.ts`** — relocate `quantizeAim` to `touch.ts`; add `createGamepadInputSource`. Red-first: a new test driving a fake `GetGamepads` (stick deflected, button pressed) proves the standalone source produces a correct, quantized, edge-detected `InputState` with no keyboard/mouse/touch machinery present at all — new ground, since production code today never runs `gamepad.ts` detached from `input.ts`'s merge.
2. **`src/game/replay.ts`** — `EncodedTick`/`encodeTick`/`decodeTick`, `REPLAY_SCHEMA` → 2, `replayMetaFor` derives `playerCount` off `world.tanks`, `InputSource`/`RecordingInput` genericized to `InputState[]`, `replayTrace` switches to `stepInputs`/`decodeTick`. Red-first: extend `replay.test.ts` with a two-slot round-trip (mirroring `step-inputs.test.ts`'s "each player flies its own input" test at the encoding layer) and a driver-adjacent regression proving a 1-length-array replay under the new schema reproduces byte-identical output to the pre-change `step()`-based replay for the same scripted input.
3. **`src/game/driver.ts`** — `DriverDeps.input: { sample(): InputState[] }`, `step` → `stepInputs`. Red-first: (a) a two-player fixture world with two fake sources, asserting each `controlledBy` tank moved per its own slot's input (the driver-layer twin of `step-inputs.test.ts`'s "pairs by position" test); (b) the N=1 structural-identity regression named in §3.
4. **`src/game/loop.ts`** — `coop` flag wiring, `slots` array, `effectiveInput.sample(): InputState[]`, per-slot `setPlayerPosition`, gamepad-merge/coop exclusivity, sandbox exclusion, slot-1 teardown (`dispose()`, alongside the existing `input.dispose()` at loop.ts:1218). Red-first: extend `loop.test.ts` with (a) `coop` off leaves every existing test's fakes and assertions unchanged (the regression signal that the input-shape change didn't leak); (b) `coop` on calls `deps.levels.world(...)` with `playerCount: 2` and each slot's `setPlayerPosition` gets its own tank's position — this is the §5 integration test tying routing to `loadArena`'s real spawn order; (c) `coop=1` + `gamepad=1` together construct exactly one gamepad reader (spy on `getGamepads`/reader construction count); (d) `coop=1` + `level=sandbox` degrades to a single-slot session.
5. **`tools/mutate/manifest.json`** — re-measure `replay-recorder-wraps-the-raw-controller` per §4's finding; update `expectFailures`/`why` to what's actually observed, not assumed.
6. **Full gate**: `npm test`, `npm run build`, `npm run test:gl`, `npm run mutate`, and `npx vitest run tools/baseline/trace.test.ts` to confirm `BASELINE_HASH` unmoved — safe by construction (`step`/`stepInputs`/`loadArena`-at-default are all untouched, and `tools/baseline/trace.ts` imports `src/sim` only, never `driver.ts` or `replay.ts`), kept as the empirical-confirmation habit CLAUDE.md itself follows rather than trusted on structure alone.

**Pins that move**, stated with what changes them: `REPLAY_SCHEMA` (1→2, deliberate); `DriverDeps.input`'s type (touches the single `sample(): InputState` fake in `driver.test.ts`, one call site); `InputSource`/`RecordingInput.sample()`'s return type (touches `replay.test.ts`'s `scriptedInputs` helper); `tools/mutate/manifest.json`'s `replay-recorder-wraps-the-raw-controller` entry (§4); `src/game/devflags.test.ts`'s `DEV_FLAGS_OFF`-derived boolean sweep picks up `coop` automatically (closes itself, no manual edit). **Unmoved, argued and to be verified**: `BASELINE_HASH`; every `step-inputs.test.ts` pairing-rule assertion (sim-side, untouched by this PR); the foundation PR's render-seam and `loadArena` behavior (no changes proposed to `src/sim/arena.ts` or `render/entities.ts` here).

**Defers to a later (semantics) PR, named explicitly**: `resolveStatus`'s P1-only win/lose, shared `world.lives`, per-player attribution in `stats.ts`/`haptics.ts`/`director.ts`/HUD, P2 invincible, a P2-specific gamepad-connect toast, AI targeting awareness of two humans, sandbox co-op support, and any N>2 assignment (gamepad[1], keyboard split) — all consistent with what the foundation plan and CLAUDE.md already name as out of scope for input routing.

### Forks for the owner

None — input mapping, the flag's boolean shape, the driver's always-list-shaped boundary, the schema bump over a migration path, and the sandbox exclusion are all decided above with a stated reason.
