## PR 1 — N-player foundation: `players=N`, 4-slot rings, idle degrade

**What was already true, read from source, not assumed.** `loadArena`'s co-player loop
(`src/sim/arena.ts`) is `for (let i = 1; i < playerCount; i++)`, unconditioned on any
hardcoded "2" -- it was already N-capable in code, confirmed by this PR without
changing a line of `arena.ts`'s own logic. The only real ceiling was `devflags.ts`'s
`coop: boolean` (locked `playerCount` to exactly 2 via `loop.ts`) and
`IDENTITY_RING_COLORS`'s 2-entry array (`src/render/entities.ts`).

**Flag: clean break, `coop` deleted, `players: number | null` added.** `coop` had zero
real users -- dev-flag-only, no menu path. Parsed like `asQuality`, not like the
boolean sweep (`players` is valued, not `isOn`): accepts 1 (explicit no-op, matches
omission) and 2-4; rejects anything else (0, negative, non-integer, 5+) to `null`,
falling back to the unflagged default of 1 -- `asQuality`'s reject-to-null idiom, not
clamping. `loop.ts`'s `coopActive` boolean generalized to
`playerCount = level === 'sandbox' ? 1 : (deps.devFlags.players ?? 1)` -- the sandbox
exclusion folded directly into `playerCount` rather than kept as a second boolean, so
every site that read `coopActive` generalizes uniformly to `playerCount >= 2` /
`playerCount`. `FLAG_REGISTRY`'s `coop` entry replaced with `players`; `docs/dev-flags.md`
regenerated via `npm run devflags:doc`.

**Spawn ring at N=3/4 -- MEASURED, not merely traced.** `findCoPlayerSpawnCell`
generalizes as expected: `arena.test.ts` now calls `loadArena(arena, 3)` and
`loadArena(arena, 4)` for all 5 shipped arenas, asserting the concrete resolved cell.
Result, per arena (all 5: arena-01 through arena-05):

- P3 resolves to ring-1-S (`(p1Row + 2, p1Col)`), matching the design's prediction.
- P4 resolves to ring-1-W (`(p1Row, p1Col - 2)`), matching the design's prediction.
- Every one of the 5 arenas has BOTH candidates open at ring 1 -- no arena falls
  through to ring 2 or the co-locate fallback. (arena-01/02/03 share a P spawn at
  (row 22, col 16): P3 -> (24, 16), P4 -> (22, 14). arena-04/05 share (row 28, col 22):
  P3 -> (30, 22), P4 -> (28, 20).)

The synthetic cramped fixture (`arena.test.ts`'s own describe block) is extended with
two new N=4 fixtures beyond the existing N=2 ring-2/co-locate pair: one that forces P2
to succeed at ring-1-E while P3 must escalate to ring-2 (every other ring-1 direction
blocked) and P4, finding ring-2-E already claimed by P3, escalates further to
ring-2-S; and one that boxes every ring in solid walls and shows P2, P3 AND P4 all
co-locate at the SAME cell as P1 -- the co-locate fallback does not check `claimed`,
unlike every ring search ahead of it, which is worth pinning explicitly since it is not
obvious from reading the ring-search code alone.

**Ring colors: extended, not invented from nothing.** `IDENTITY_RING_COLORS` grew from
`[0x3fd0ff, 0xff8a1e]` (unchanged) to `[0x3fd0ff, 0xff8a1e, 0xff4d2e, 0x9d3bff]`. Slot 2
is a bright vermillion, slot 3 a reddish-purple pushed toward violet -- the two
remaining Okabe-Ito-adjacent hues past blue/orange, re-brightened the same way the
existing two were. Checked by hand (RGB Euclidean distance and hue angle, not asserted
-- the test remains inequality-only, per the design's own instruction not to hardcode a
distance threshold) against the existing two rings, the 7-color roster
(`brown`/`grey`/`teal`/`olive`/`green`/`yellow`/`player`) and the `UNSTYLED_SLOT_HEX`
placeholder (`#c23b8f`): slot 2 sits only ~20 degrees of hue from slot 1's own orange
(both are inherently warm/red hues in this part of the palette -- Okabe-Ito's own
orange and vermillion are ~18 degrees apart, so this is close to the closest available
pairing within "vermillion territory," not a miss), and slot 3's hue was moved off the
literal reddish-purple hue (~325 degrees) and toward violet (~270 degrees)
specifically because true reddish-purple territory already sits close to the
placeholder's own hue (~323 degrees). Review recomputed the margins from the actual hexes:
the tightest cross-family pairing is slot2-vs-brown at ~118 RGB units but only ~20.8
degrees of hue -- comfortably distinct in the additive-render context but NOT the
"~45-degree floor" an earlier draft of this paragraph claimed; the tightest pairings
overall (slot0-vs-player ~21.0 degrees, slot0-vs-teal ~19.2 degrees) are pre-existing,
not introduced here. (The Okabe-Ito orange/vermillion reference gap measures ~15
degrees from the canonical hexes, not ~18 -- the conclusion it supports only
strengthens under the correction.) `entities.test.ts`'s distinctness
sweep extended: a new `fourPlayerWorld` fixture renders all 4 rings and asserts all 6
pairwise comparisons distinct, and the existing roster/placeholder sweep already
iterates `IDENTITY_RING_COLORS` directly, so it covered all 4 entries with no edit once
the array grew.

**Idle degrade for unfilled slots -- built as designed, and the bug it fixes was run,
not just traced.** Naive reuse of `createGamepadInputSource(() => [])` is wrong: with
no pad ever present, `aim` never leaves its `{0,0}` construction default, and
`driveTank` (`world.ts`) computes `aimDir = vsub(input.aim, player.pos)`, nonzero for
any tank not spawned at the origin -- the turret slews toward world-origin and sticks.
This is empirically confirmed in three places, each added this PR:

1. `src/sim/world.test.ts`'s `driveTank: a literal {0,0} aim is not a neutral` --
   the mechanism, pinned once, independent of which source produces the literal.
2. `src/input/gamepad.test.ts`'s new `RED-FIRST` test -- proves `createGamepadInputSource`
   with no pad ever connected reproduces the bug through the real sim (verified
   red against the pre-fix source, then green after the fix, by hand during
   development).
3. `src/game/loop.test.ts`'s `createIdleInputSource` describe block -- same red/green
   verification against the new source.

A fourth check, added at the WIRING layer (`loop.ts`'s own `slots` construction, not
just the unit-level source), initially shipped tautological: it read
`h.rec.builtWorlds[0]`, the object `deps.levels.world` returned at boot, which the
driver never mutates in place (`step` clones every tick; the driver reassigns its own
internal `curr`), so the assertion passed regardless of what the idle source actually
did. Caught in review before merge, not after: fixed to read
`h.rec.renders.at(-1)!.curr.tanks` (the live world), and re-verified red-first against
a naive always-`{0,0}` source (turretAngle kept moving, `-2.13` vs. the settled
`-0.13`) before trusting it green. Fixing it also surfaced a real, second interaction:
`driver.ts`'s `onSimulated` (and so the idle source's first `setPlayerPosition` call)
runs only after the batch of ticks one `fireFrame` call simulates, not before it -- so
a test's first `fireFrame` call unavoidably samples the idle source before it has ever
learned its tank's position, reproducing the documented boot-time transient for that
whole batch. Both wiring-layer tests now take a small warm-up frame first, then assert
`turretAngle` is unchanged across many more ticks -- "holds steady," not "equals 0."

`createIdleInputSource(): PlayerInputSource` (`loop.ts`) stores `lastPos` via
`setPlayerPosition` and echoes it back RAW (not run through `quantizeAim`) as its own
`aim`, so `aimDir` resolves to exactly `{0,0}` and the turret holds. `loop.ts` fills
slots 2..`playerCount`-1 with it; slot 1 keeps the existing single-gamepad wiring.

**Decided by reading, then shipped:** `createGamepadInputSource`'s OWN no-pad default
was ALSO fixed, not left as a known residual for slot 1. `reader.connected()`
distinguishes "no pad ever" from "pad connected, stick centred" -- both report
`poll().aim === null`, so the existing `if (gp.aim !== null)` check alone cannot tell
them apart, but `connected()` can: the raw-position-echo fallback fires only when
`!reader.connected()`, leaving the connected-but-centred case (a real pad at rest)
holding its last real aim exactly as before. This was cheap (a few added lines, one
extra branch) and preserved all 7 pre-existing tests in `gamepad.test.ts` unmodified
(verified: `npx vitest run src/input/gamepad.test.ts` before and after showed the same
7 tests passing, plus 4 new ones), so both fixes shipped in this PR rather than only
the loop.ts-level one.
